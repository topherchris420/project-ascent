Run `npm run db:migrate` from the project root. Without DATABASE_URL this initializes the local SQLite schema; production refuses SQLite. With DATABASE_URL (or a separate MIGRATION_DATABASE_URL), the script applies numbered SQL files once inside an advisory-locked transaction. The migration identity needs permission to install PostGIS and create schema objects. Never use that privileged identity as the application connection.

For a new dedicated database, provision a separate application login with NOSUPERUSER, NOBYPASSRLS, NOCREATEDB and NOCREATEROLE. Set its password through your secret manager or an interactive database administrator session; no password belongs in a migration file. Grant CONNECT on the dedicated database, USAGE on the application schema, and SELECT, INSERT, UPDATE, DELETE on tenants, users, sessions, rate_limits, workspaces, documents, property_locations, billing_events, team_invitations and api_keys. Do not grant schema CREATE, role administration, or ownership privileges that permit disabling the RLS policies. Reapply the explicit table grants after introducing a new migration table.

The application checks that its role is neither superuser nor BYPASSRLS and that all six tenant tables (workspaces, documents, property_locations, billing_events, team_invitations and api_keys) have enabled and forced RLS. Every tenant transaction sets app.tenant_id with SET LOCAL semantics; pooled connections cannot retain a tenant after commit. The authentication registry (users, sessions, tenants) and rate limits are server-only global tables. No database credential is sent to the browser.

Use TLS with certificate validation for a remote production database (PGSSL=require when not already required by your connection URL). Configure APP_ORIGIN as the exact HTTPS deployment origin, APP_ENCRYPTION_KEY as base64 encoding of 32 random bytes, and CRON_SECRET for the market job. Keep document encryption keys stable and backed up; rotation and backups require an operational procedure before real customer deployment.

Migration 001 creates PostGIS projections and tenant workspace/document isolation. Migration 002 adds durable Stripe event deduplication and one-use team invitations. Migration 003 adds hashed, scoped enterprise API credentials with tenant RLS. PostgreSQL execution remains unverified until an authorized database is configured; the local automated suite verifies SQLite persistence and application authorization boundaries.

## Sharing an existing PostgreSQL service safely

Use a dedicated `ascent` database, not another application's database or public schema. Do not change the other application's role, password, tables, grants or connection URL. A database on the same service shares its resource limits; this does not create independent compute capacity or a separate backup policy.

On Neon, console-created roles inherit administrative membership. Create the restricted runtime login using SQL instead, as described in [Neon's database access guide](https://neon.com/docs/manage/database-access). Keep administrator credentials out of the application environment. Revoke public schema creation and public connection access only on the newly created Ascent database; do not revoke privileges on the existing application database.

After applying migrations and granting the runtime role access, run the opt-in PostgreSQL acceptance check:

```powershell
npm.cmd run verify:postgres -- --database=ascent
```

It requires `DATABASE_URL` for the restricted role and the stable `APP_ENCRYPTION_KEY`. The database name in the URL must exactly match the explicit `ascent` argument (or an `ascent_...` name). It refuses SQLite and runs under production database safeguards. It creates two disposable synthetic accounts, checks authentication, real RLS behavior, PostGIS, concurrent edits, encrypted documents, JSONB-stable CMA calculations, deterministic evidence assistance and HTML report export, then removes only accounts generated by that run. It makes no property-provider or inference requests and prints no connection string or token. It is a direct application/database integration check, not a deployed browser acceptance test. A failed cleanup requires an administrator to inspect that run's synthetic accounts; it never removes unrelated data.

Do not copy an entire development SQLite file into production. Development records, live-provider access grants and encryption settings require a separate reviewed migration.
