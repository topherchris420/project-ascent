# Account security and recovery

The existing account system now uses OTPAuth for standard six-digit, 30-second TOTP authenticator codes (SHA1, ±1 time-step window). It rejects reused time steps atomically, including concurrent logins. Setup requires the current password and expires in 15 minutes; confirmation proves possession. Secrets and reset-mail payloads use AES-256-GCM under the stable server `APP_ENCRYPTION_KEY`. Eight 128-bit recovery codes are shown once and stored only as hashes. Each recovery code is consumed atomically.

Production owners and agents must enroll before opening a private workspace. Password-only enrollment sessions can access account security and logout, but not workspace APIs. Enabling MFA revokes all sessions; a new login requires a fresh authenticator code or an unused recovery code. Isolated server-created fictional demonstration tenants are exempt; client registration cannot set that trusted flag. Viewers can opt in. Existing enabled MFA is required for every role, in every environment.

The account UI is `/account/security`; sign-in accepts an authenticator or recovery code. A password reset keeps enabled MFA and unused recovery codes intact. Losing both the authenticator and all recovery codes requires an independently verified operator recovery procedure; there is deliberately no password-only MFA bypass or self-serve disable endpoint. Email ownership verification and device/session management remain future work.

## Deployment order

1. Back up the authorized database and verify recovery access. Apply migration `004_account_security.sql` using the separate migration identity **before deploying the new account routes**. Grant the restricted runtime role SELECT/INSERT/UPDATE/DELETE on `account_security`, `session_assurance`, `password_resets`, `auth_mail_outbox`. These are server-only global identity tables like `users` and `sessions`; never grant direct browser/database access. The six workspace tenant tables retain forced RLS.
2. Keep the stable `APP_ENCRYPTION_KEY` and exact `APP_ORIGIN`. Configure server-only `RESEND_API_KEY` and `AUTH_MAIL_FROM` for a sender/domain you have verified with the mail provider. No mail account/domain was provisioned or email sent during this work. Never paste secrets into Git or a chat.
3. Confirm the application role can use the new tables. On the deployed HTTPS origin, register a designated test account, enroll, save recovery codes, sign out/in, prove an old session is blocked, and test recovery from your own mailbox. Test wrong/expired/reused links and codes, origin denial and throttling. Record a sanitized receipt before claiming deployed acceptance.

## Password reset

`/account/recovery` requests a one-use 256-bit link, valid 30 minutes. Only SHA-256 tokens are stored in `password_resets`. Existing and absent accounts receive the same response; email work occurs after that response through an encrypted outbox. Requests are throttled per account and IP. Missing delivery configuration returns a clear 503 and mints no token. Links use a fragment instead of a query parameter; the recovery page removes the fragment, uses no-referrer policy, and submits the token only in the reset POST body.

The Next.js `after` hook drains the small outbox after a successful request. An authenticated `/api/cron/auth-mail` GET is also available for an operator retry with the existing long `CRON_SECRET`; it is not scheduled more frequently than the hosting plan permits. Claim/delete is atomic, so an item is never sent twice. Queued requests are bound to the password version when requested; changing the password also invalidates older queued requests before delivery. Network/rejected mail is counted without logging addresses/tokens; failed delivery requires requesting a fresh link. Monitor those failures. No claim of guaranteed delivery is made.

Resetting changes the password, atomically consumes all reset links and revokes every session without automatically signing in or removing MFA. Pending unconfirmed enrollment is cleared. Passwords retain the existing scrypt storage. Recovery templates are plain text. The email transport is [Resend’s documented endpoint](https://resend.com/docs/api-reference/emails/send-email); factor generation uses [OTPAuth](https://github.com/hectorm/otpauth). The lifecycle follows [OWASP recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) and [MFA guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html). These local implementation checks do not replace an independent security audit.
