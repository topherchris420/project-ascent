# Capability and evidence matrix

This compares the delivered independent implementation with Homesolo's **publicly observable October 15, 2026 baseline**. It does not compare against an authenticated Homesolo account, private source, licensed live data or historical versions. See [reconstruction.md](reconstruction.md) and [evidence-ledger.md](evidence-ledger.md) for exact REA records.

**Original evidence classes:** O = executed public observation; S = rendered fictional sample; C = published claim; U = unknown. Homesolo's public `/demo` samples are inside deliberately inert wrappers. Their controls establish intended information architecture, not actual authenticated execution. An implemented Ascent feature is not automatically a verified improvement over the private product.

**Successor evidence:** code paths and named tests below establish implementation and tested synthetic behavior. [Verification results](verification-results.md) records the final executed run; [benchmark-results.json](../evidence/benchmark-results.json) identifies its own timestamp, runtime and fixture. Credentials and live service tests remain explicitly separate.

## What has actually been demonstrated

The source and test artifacts demonstrate a functioning independent synthetic workflow rather than a collection of inert screens: account persistence, property research, interactive pricing, saved/approved CMA, client note continuity, offer draft approval, reviewed deadline extraction, sourced assistant response and report response. Browser tests also exercise registration/logout/login, mobile navigation, selected automated accessibility scans, nonblocking pending verification and shared DMV/Austin property/CMA interfaces.

These are verified properties of the delivered local build. They do **not** prove superiority over Homesolo's authenticated product. New graph, fabric, usage and evaluation infrastructure are implementation differentiators relative to the captured public baseline; absence from public evidence does not establish absence from the original private system.

Enterprise API key administration uses `GET /api/integrations/keys` → `{keys}`; `POST {action:"create",name,scopes,expiresInDays?}` → `{key,token}`; and `POST {action:"revoke",id}` → `{keys}`. Scopes are `properties:read` and `cmas:read`; expiry defaults to 30 days with a 90-day maximum and 20 active keys per organization. The read endpoints accept optional `q`, `limit` (1–100) and `offset` (0–10,000). Each successful authorized read reserves a `fabricQueries` usage unit; no API key creates provider rights or approves a professional license. This is read-only integration infrastructure, not an unrestricted MLS redistribution API.
